## Добавление странцы на сайт

### Новости

Скопировать директорию:

```
./archetypes/0_to_copy_news -> ./content/news/
```

команда:

```bash
cp -a ./archetypes/0_to_copy_news ./content/news/new_post
```

### Партнеров

Скопировать директорию:

```
./archetypes/0_to_copy_news -> ./content/partner/
```

команда:

```bash
cp -a ./archetypes/0_to_copy_news ./content/partner/new_partner
```

### Описание структуры страницы:

```
1_to_copy_news          <- Директория страницы с ее содержимым и файлами
├── images              <- Фото для слайдов (сорировка сладов в алфовитном порядке по названию)
├── index.md            <- Контент страницы
└── preview.webp        <- Превью страницы
```

В корень директории при необходимости добавляються все файлы которые используются на странице

### Убрать страницу из поиска через robots.txt

В front matter нужных страниц добавьте параметр `disallow: true`:

```
disallow = true # Страница, которую нужно скрыть
```

### Настройка IndexNow для GitHub Pages

Для работы с IndexNow необходимо просто заменить значение переменной `INDEXNOW_KEY` в секретах GitHub Actions.
Больше ничего делать ну не надо.

'GitHub → Repository → Settings → Secrets and variables → Actions → Secrets'

```
Secrets
└── INDEXNOW_KEY
    └── 42e02184e285e8a4d0a

Variables
└── SITE_URL
    └── energo-effect.pro
```

## Замена фоновой картинки баннера

При смене фонового изображения баннера нужно обновить **три места**, иначе preload и CSS разойдутся, и картинка загрузится дважды.

### `<link rel="preload">` — атрибут `href`

```html
href="{{ `images/НОВЫЙ-ФАЙЛ.webp` | absURL }}"
```

### `<link rel="preload">` — атрибут `imagesrcset`

Указать **новые URL и реальные ширины** файлов в пикселях:

```html
imagesrcset="{{ `images/НОВЫЙ-ФАЙЛ.webp` | absURL }} ШИРИНА_w, {{
`images/НОВЫЙ-ФАЙЛ-540.webp` | absURL }} ШИРИНА_w"
```

### ⚠️ Что менять НЕ нужно

- **`imagesizes`** — если брейкпоинты (`540px`, `720px` и т.д.) остались прежними.
- **Структуру `<link>`** — тег остаётся один, с `imagesrcset` и `imagesizes`.

## Размер превью для статей и новостей

Превью для статей и новостей должны иметь размер **306×173 px**.

Для приведения изображения к нужному размеру без обрезки используется ImageMagick:

```bash
magick preview.webp -resize 306x173\! preview.webp
```

# Принципы проекта Hugo-EnergoEffect

## 1. Общая архитектура

- **Используем стандартные возможности прежде собственных решений.** Сначала Bootstrap, Hugo и их штатные механизмы, затем расширения и только после этого собственный код.
- **Не изменяем базовые значения используемых систем.** Если стандартного значения недостаточно — расширяем систему, не меняя её существующее поведение.
- **Код должен быть системным.** Новое правило или компонент создаётся для решения класса задач, а не одной конкретной ситуации.
- **Не усложняем архитектуру без необходимости.** Если задачу уже решает Bootstrap или Hugo — не создаём собственный механизм.
- **Визуальный результат является критерием качества.** Стандартизация не должна ухудшать дизайн, читаемость или UX.

---

## 2. Bootstrap и CSS

- **Bootstrap 5.3.8 — основа UI.**
- **Bootstrap utilities имеют приоритет над собственным CSS.**
- **Custom CSS используется только для уникального дизайна**, которого нет в Bootstrap.
- **Не переопределяем глобально Bootstrap ради одного компонента.** Для уникального поведения используем отдельный класс.
- **Используем mobile-first и стандартные Bootstrap breakpoints.**
- **Не дублируем стили между breakpoint'ами.** Добавляем только реально изменяющиеся свойства.
- **Используем единую шкалу размеров проекта**, а не произвольные значения.
- **16:9 — стандартное широкое соотношение проекта.**
- **Не используем magic numbers без необходимости.** Если значение повторяется или является частью системы — оно должно быть представлено как переменная, utility или элемент шкалы.

---

## 3. HTML и accessibility

- **Используем семантический HTML прежде ARIA.**
- **Не добавляем ARIA-атрибуты без необходимости.** Если нативный HTML уже обеспечивает нужную семантику — дополнительных атрибутов не требуется.
- **Не добавляем `aria-label`, если видимый текст уже является доступным названием элемента.**
- **Декоративные изображения и иконки не должны попадать в accessibility tree.**
- **HTML-структура компонента должна оставаться простой и предсказуемой.**

---

## 4. Hugo

- **Используем Hugo Pipes для обработки ресурсов.** SCSS и JavaScript проходят через штатный pipeline Hugo.
- **`assets/` используется для ресурсов, которые обрабатываются Hugo.** Например: SCSS, JS, изображения, SVG.
- **`static/` используется для файлов, которые должны быть опубликованы без обработки.**
- **Не смешиваем активные и архивные ресурсы.** Неиспользуемые файлы не должны находиться среди рабочих ресурсов.
- **Не используем широкие `resources.Match` без необходимости.** Обрабатываем только действительно необходимые ресурсы.
- **Используем `resources.Get` для управляемого доступа к ресурсам.**
- **Обязательные ресурсы должны проверяться при сборке.** Отсутствие критического файла должно приводить к ошибке Hugo, а не к тихому пропуску.
- **Внутри `with resources.Get` учитываем изменение контекста `.`.** Для глобального контекста используем `site` или `$`.
- **Для ссылок на обработанные Hugo-ресурсы предпочитаем `.RelPermalink`.**
- **Статические ресурсы и результаты Hugo Pipes должны иметь понятную ответственность:** исходник → обработка → production-ресурс.
- **CSS и JS в production минифицируются и fingerprint'ятся.** Это обеспечивает оптимизацию и корректное cache busting.
- **Используем `integrity` для fingerprint'ированных ресурсов**, когда ресурс подключается непосредственно из сгенерированного pipeline.

---

## 5. Изображения и производительность

- **Контентное изображение — `<img>`, декоративное изображение — CSS background.**
- **Для изображений указываем `width` и `height`, когда размеры известны.** Это уменьшает вероятность CLS.
- **Используем современные форматы изображений**, прежде всего WebP/AVIF для растровых изображений и SVG для векторной графики.
- **Используем `srcset` и `sizes`, когда изображение имеет разные варианты отображения.**
- **LCP-изображение не загружаем через `loading="lazy"`.**
- **Остальные подходящие изображения загружаем лениво.**
- **Оптимизация производительности рассматривается как часть архитектуры, а не как последний этап разработки.**

---

## 6. JavaScript

- **Используем npm и Hugo `js.Build` для современного JavaScript.**
- **Bootstrap подключается как npm-зависимость, а не как вручную скопированный vendor-файл.**
- **Legacy-библиотеки изолируются от современной JS-сборки**, пока они действительно необходимы.
- **Не добавляем библиотеку, если задачу можно решить штатными средствами Bootstrap или браузера.**
- **JS собирается, минифицируется и fingerprint'ится для production.**
- **Скрипты, которым не требуется блокировать построение страницы, подключаются с `defer`.**

---

## 7. Git и структура проекта

- **Репозиторий должен содержать только необходимые для разработки и сборки файлы.**
- **Сгенерированные production-файлы не должны становиться источником истины.** Источником являются исходники Hugo/SCSS/JS и конфигурация проекта.
- **Изменения должны быть логически разделены по задачам.**
- **Git commit'ы должны описывать завершённое изменение и следовать Conventional Commits.**
- **Названия и структура файлов должны отражать их назначение, а не историю появления.**

---

## 8. GitHub Pages / deployment

- **GitHub Pages используется как production-площадка проекта.**
- **Deployment выполняется автоматически через GitHub Actions после прохождения production build.**
- **В GitHub Actions используется тот же production-процесс, который должен воспроизводиться локально.**
- **Deployment не должен выполнять скрытые ручные действия.** Сборка должна быть воспроизводимой из состояния репозитория.
- **В production используется production-конфигурация Hugo:** minification, fingerprinting и остальные необходимые оптимизации.
- **Ошибки Hugo, Sass, JS или отсутствующие обязательные ресурсы должны останавливать deployment.** Некорректный сайт не должен публиковаться.

---

## 9. Проверка перед deployment

- **Перед deployment выполняется production build проекта.**
- **Перед публикацией проверяется результат сборки, а не только исходный код.**
- **Перед deployment выполняется проверка Google PageSpeed Insights.**
- **Проверяем как минимум Mobile и Desktop.**
- **Особое внимание уделяем Core Web Vitals:** LCP, CLS и INP.
- **Найденные проблемы PageSpeed устраняются на уровне архитектуры**, если они вызваны кодом проекта, а не маскируются локальными workaround'ами.
- **Оптимизация не должна ухудшать доступность, SEO или визуальное качество сайта.**

---

# Главный принцип

> **Используем стандартные возможности Hugo, Bootstrap и браузера как основу; расширяем их только там, где это действительно необходимо; сохраняем единые правила проекта и проверяем результат как по коду, так и по производительности.**
